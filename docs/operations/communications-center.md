# 公告与站内消息运维说明

Nyauth 的沟通能力分为三类，各自承担不同语义：

- 全站横幅适合短时、即时、全局可见的运行提示。它是单例运行时设置，可通过 SSE 热更新，不进入公告历史。
- 持久公告适合版本说明、长期通知和管理员提示。公告具有草稿、已发布、已归档状态，可设置受众、级别、置顶以及独立的开始和结束时间。
- 个人站内消息由有界事件目录生成，当前覆盖密码、邮箱、TOTP、Passkey、外部身份、OAuth 授权撤销、设备授权和应用发布者可信状态变化。

## 公告生命周期

新公告首先保存为草稿。发布要求标题和正文均非空；发布后的公告立即或在 `starts_at` 到达后对目标受众可见。`starts_at` 和 `ends_at` 均可独立省略。归档只接受已发布公告，归档后不再出现在用户列表；归档是终态，不能通过重复发布 API 恢复。

管理修改使用 `expected_revision` 做乐观并发控制。revision 不一致返回 `409 announcement.revision_conflict`，前端保留草稿并要求重新加载。公告创建、修改、发布或归档与对应审计 outbox 写入同一 PostgreSQL 事务。

用户已读状态不为每个公告预先复制收件记录。用户实际阅读时，`announcement_reads` 保存当时的公告 revision；已发布内容后续发生修改会递增 revision，因此对已读用户重新显示为未读。用户只能为当前对自己可见、已发布且处于展示窗口内的公告写入回执。

## 统一消息中心

`GET /api/messages` 在 PostgreSQL 中合并当前用户的未过期站内消息和可见公告，然后按统一的 `occurred_at,id` 顺序筛选与分页。这保证“全部”页签在跨页时不会漏项或重复。接口支持 `kind`、`read`、`severity`、`q`、`from` 和 `to` 筛选，时间参数必须使用 RFC3339。

`POST /api/messages/read-all?kind=...` 按全部、站内消息或公告分类原子保存已读状态。对公告只处理当前可见且处于展示窗口内的 revision；对尚未开始、已结束或受众不匹配的公告不预先写回执。

## 内容安全

公告和个人消息只使用服务端渲染的安全 Markdown。原始 HTML、图片、协议相对链接、脚本链接和非 HTTPS 外部链接都会被拒绝；站内链接必须使用 `/` 开头的根相对路径。普通用户 API 只返回渲染后的 HTML，不返回 Markdown 源文、创建者或修改者 ID。

前端使用 `{@html}` 的内容仅来自上述服务端渲染结果。数据库中的内容不能绕过相同的写入校验；管理端预览也复用同一个渲染器。

## 投递与故障语义

个人消息在对应安全或 OAuth 操作已经成功提交后写入。消息写入失败会记录结构化服务端错误，但不会回滚密码、MFA、Passkey、身份或授权等已经成功的安全操作。这是明确的可用性边界：站内消息是辅助通知，不是业务提交凭证；审计日志仍是安全事件的权威记录。

顶部未读数由 PostgreSQL 重新计算。浏览器优先连接 `/api/notifications/events`，连接失败后每 30 秒轮询一次 `/api/notifications/unread-count`；SSE 只发送三个低敏感计数，不发送标题、正文或用户资料。服务端限制单实例 SSE 连接数，超过限制时客户端会自动使用轮询。

`user_notifications.dedupe_key` 只用于确有稳定业务标识的事件。普通重复操作不会被无依据地合并。通知类型由 `internal/notification` 的代码目录限定，未知类型在写入前失败关闭。
